# Use RabbitMQ via MassTransit as the message broker

The Notification API needs to hand off `NotificationRequested` events to independent Channel Services without waiting on them. We picked RabbitMQ (topic exchange, one queue per Channel) over Kafka, NATS, and Azure Service Bus, and MassTransit over the raw `RabbitMQ.Client` SDK. Kafka's log-and-replay model doesn't fit a task-style fan-out with no replay requirement, and would add significant operational weight for a learning environment; NATS and Azure Service Bus were rejected to keep the environment cloud-agnostic and running entirely in docker-compose. MassTransit was chosen over raw `RabbitMQ.Client` because it provides retry policies, dead-lettering, and outbox integration as configuration rather than hand-rolled code, which is the point of the exercise: learning the production patterns, not reimplementing AMQP plumbing.

**Version pin**: use MassTransit **8.5.10** (the last free line), not 9.x — MassTransit moved to a commercial license starting at v9. This is deliberate, not an oversight: pulling in a paid dependency would contradict the point of a free, self-contained learning environment. Confirmed via [Research: MassTransit outbox, retry, and DLQ configuration for RabbitMQ + EF Core/Postgres](https://github.com/peterderkoala/messagebroker_demo/issues/2).
